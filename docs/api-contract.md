# Prototype API contract v1

This specifies our backend, not organizer endpoints. FastAPI + SQLite; React + TypeScript + Vite client. Base `/api/v1`, UTF-8 JSON. No demo authentication. Requests/responses use snake_case. Reject unknown request fields. Required fields are required even when nullable; no implicit defaults except explicitly stated below. IDs are opaque strings; fixture IDs are illustrative. Times generated by our API are RFC3339 UTC. Source timestamps are preserved verbatim.

## Common types and validation

`Language = "RU" | "KZ" | "EN"`; `Channel = "agent chat" | "voice call"`; `Speaker = "client" | "operator" | "bot" | "system"`.

`Evidence = {message_ids: string[], inspected_ranges: {start_message_id:string,end_message_id:string}[]}`. Ranges are inclusive, ordered by ordinal and confined to this conversation. At least one message or range is required for every judgment. A missed action requires at least one inspected range; rationale says where it was expected. N/A rationale identifies the configured condition. Client appeal evidence is optional (defaults to empty arrays); reviewer replacement evidence is mandatory.

`SourceRecord = {conversation_id:string, channel:Channel, language:Language, transcript:{timestamp:string,speaker:Speaker,text:string}[], audio_url:string|null}`. Transcript must be nonempty; source ID/text must be nonblank. Chat timestamp matches MM:SS (minutes may exceed 59, seconds 00–59); calls require ISO8601 including timezone. Do not sort or rewrite source timestamps. Chat audio_url must be null; call audio_url may be null if unavailable, otherwise an absolute HTTP(S) URL. Never invent audio offsets from wall-clock timestamps; use external player links unless source-relative timing is known.

`Conversation = {conversation_id:string, source:{kind:"dataset"|"upload",group_id:string|null,conversation_id:string},channel:Channel,language:Language,audio_url:string|null,messages:Message[]}`.
`Message = {message_id:string,ordinal:integer,timestamp:string,speaker:Speaker,text:string}`; ordinal is contiguous, 1-based, in original array order. Internal conversation ID is distinct from source ID. Dataset identity is `(group_id, source conversation_id)`; upload IDs occupy their own namespace. Persist IDs once; assign message ID deterministically from internal conversation ID + ordinal (e.g. UUIDv5); identical reimport retains all IDs. Changed content under an existing source identity is a 409, including timestamp-only edits. Upload different content under a new source ID. Never edit transcripts in place once imported.

`Section = {section_id:string,title:string}`.
`Criterion = {criterion_id:string,section_id:string|null,title:string,wording:string,weight:number,answer_type:"boolean"|"numeric",allowed_numeric_values:number[],maximum:number|null,na_allowed:boolean,na_condition:string|null,effect:"score"|"gross_error",scale:{value:number,wording:string}[]}`.

IDs unique within checklist; section references must exist. Wording/title nonblank; weight finite and >=0. Boolean requires empty numeric values/scale and maximum null. Numeric requires distinct finite nonnegative values including 0 and maximum; maximum >0; no value exceeds maximum; exactly one nonblank scale anchor per allowed value. N/A condition must be nonblank iff permitted, otherwise null. At most one gross-error criterion; it must be boolean, weight 0, N/A false. Scoring weights need not sum to 100; normalization always applies. Empty checklists are invalid; configurations with no positive scoring weights are allowed and yield null totals. These rules allow added or replaced criteria without hardcoded criterion IDs.

`ChecklistInput = {name:string,sections:Section[],criteria:Criterion[]}`.
`ChecklistVersion = {checklist_id:string,version:integer,name:string,sections:Section[],criteria:Criterion[]}`. Version >=1. This exact shape is `fixtures/checklist.json`. Version snapshots are immutable. Keep criterion ID when editing the same criterion; give a replacement a new criterion ID. No patching a historical version.

`Judgment = {criterion_id:string,answer:"yes"|"no"|"numeric"|"na",numeric_value:number|null,rationale:string,evidence:Evidence}`. Boolean accepts yes/no; numeric accepts numeric plus an exact allowed value; na requires na_allowed and a rationale establishing its condition. numeric_value is null unless answer=numeric. Every completed result has exactly one judgment per versioned criterion, no extras. Gross-error yes means violation present. No weighted points come from the model. Valid JSON alone is insufficient: validate scale membership, IDs, evidence, types and completeness before accepting provider output.

`Score = {criterion_id:string,weight:number,raw_points:number|null,effective_weight:number|null,points:number|null}`.
`SectionScore = {section_id:string,points:number|null,maximum:number|null}`.
`Result = {judgments:Judgment[],scores:Score[],sections:SectionScore[],applicable_weight:number,total:number|null,total_unavailable_reason:null|"no_applicable_weight",gross_error:boolean|null}`.

`Evaluation = {evaluation_id:string,conversation_id:string,checklist_id:string,checklist_version:integer,status:"queued"|"running"|"succeeded"|"failed",provider:{name:string,model:string,error:ProviderError|null},created_at:string,completed_at:string|null,revision:integer,original_ai_result:Result|null,appeals:Appeal[],final_result:Result|null}`. revision starts at 1 and increments on appeal/decision mutations, not polling. original_ai_result is immutable. final_result starts as original and folds accepted reviewer changes in decision order. Pending appeals have no effect on scoring. It is a stored computed snapshot, never AI regeneration. Only succeeded evaluations have results; queued/running/failed have both null (never fabricated zero totals). completed_at is null while queued/running and set at success/failure. A successful result may still have total null if no applicable weight. gross_error is null if no gross_error criterion configured, otherwise determined from its judgment.

`ProviderError = {code:"provider_timeout"|"provider_unavailable"|"provider_auth"|"provider_rate_limited"|"provider_invalid_output",message:string,retryable:boolean}`. Timeout/unavailable/rate limit may be retried; auth/invalid output are nonretryable for this attempt. No partial scores on failure; no silent mock fallback. A new POST evaluation is an explicit retry with a new ID, preserving the failed attempt. Provider output is judgment only; transcript/provider text is untrusted content, never configuration or executable instructions. No numeric confidence, cost or failure score is invented.

`Appeal = {appeal_id:string,evaluation_id:string,criterion_id:string,comment:string,evidence:Evidence,status:"pending"|"resolved",created_at:string,decision:Decision|null}`.
`Decision = {decision_id:string,action:"confirm"|"change",reason:string,replacement:Judgment|null,created_at:string}`. For confirm replacement must be null; for change it must target the appealed criterion and validate against the pinned version. Only one appeal per evaluation+criterion (including resolved) in this prototype; other criteria may be appealed. Decision is write-once; submitting again returns 409. Comment/reason nonblank. This single-review-cycle restriction is our 24-hour scope choice, not a PDF rule.

## Score calculation (deterministic backend service)

The judgment adapter receives the exact checklist version and whole transcript, including bot/system context, and returns judgments. A separate pure calculator, also used after reviewer decisions, derives scores:

1. Applicable scoring criteria are effect=score and answer != na. `A = sum(weight)` over these.
2. For each applicable criterion, raw = weight for yes, 0 for no, or weight × numeric_value / maximum. effective_weight = weight × 100 / A; points = raw × 100 / A.
3. Excluded N/A and gross-error criteria have raw_points/effective_weight/points null. If A=0, effective_weight/points are null for all criteria; total=null and total_unavailable_reason=no_applicable_weight.
4. Otherwise total = round-half-up(sum(raw) × 100 / A, 2), total_unavailable_reason=null. Use decimal arithmetic; do not sum rounded display values. Return component numbers unrounded to JSON numeric precision; client may format to two decimals. Finite numbers only.
5. Section points/maximum are sums of normalized points/effective weights within the section; null/null if no applicable weighted contribution. Their maxima sum to 100 when all scoring criteria have sections. Unsectioned criteria still count overall. These section contributions are our convention; PDFs do not specify a section formula.
6. Gross-error flag never multiplies, caps, or zeroes total.

Fixtures: original has A=65, raw=60, total=92.31; reviewed has c07=N/A, A=60, total=100.00. The review is an illustrative human decision, not a gold-standard label. The original must remain byte-equivalent after review.

## Routes (all belong to our backend)

Lists return `{items:T[]}` in creation order, checklist lists in ID order; no pagination in the 24-hour prototype. GET responses 200. All mutations are transactional. URL IDs must refer to existing entities. Bodies below are exact; `?` denotes the only optional properties and is documentation notation, not JSON.

| Method/path | Request | Success response |
|---|---|---|
| POST `/dataset-imports` | `{group_id:string}` nonblank | 201 `{group_id:string, imported:integer, unchanged:integer, conversation_ids:string[]}` |
| POST `/conversations` | SourceRecord JSON, not multipart | 201 Conversation for new upload; 200 identical repeat |
| GET `/conversations` | optional query group_id, language; combined filters use AND | `{items:Conversation[]}` |
| GET `/conversations/{id}` | none | Conversation |
| POST `/checklists` | ChecklistInput | 201 ChecklistVersion (version=1) |
| GET `/checklists` | none | `{items:ChecklistVersion[]}` latest nonarchived version per checklist |
| GET `/checklists/{id}/versions` | none | `{items:ChecklistVersion[]}` all versions ascending, also for archived checklist |
| GET `/checklists/{id}/versions/{version}` | none | ChecklistVersion, also if archived |
| PUT `/checklists/{id}` | `{expected_version:integer,configuration:ChecklistInput}` | 201 new ChecklistVersion, version=expected_version+1 |
| DELETE `/checklists/{id}` | query expected_version (required integer) | 204 no body; soft archive, preserve all referenced versions |
| POST `/evaluations` | `{conversation_id:string,checklist_id:string,checklist_version:integer}` | 202 Evaluation initially queued; Location `/api/v1/evaluations/{id}` |
| GET `/evaluations` | optional query conversation_id | `{items:Evaluation[]}` |
| GET `/evaluations/{id}` | none | Evaluation (poll until succeeded/failed) |
| POST `/evaluations/{id}/appeals` | `{expected_revision:integer,criterion_id:string,comment:string,evidence?:Evidence}` | 201 Appeal |
| GET `/appeals` | optional query status=pending\|resolved | `{items:Appeal[]}` |
| GET `/appeals/{id}` | none | Appeal; use evaluation_id to open original/result/transcript |
| POST `/appeals/{id}/decision` | `{expected_revision:integer,action:"confirm"\|"change",reason:string,replacement:Judgment\|null}` | 200 Evaluation including resolved appeal, decision, recalculated final_result and incremented revision |

GET checklist versions is also the checklist read operation; PUT creates a complete replacement snapshot. Archived checklist cannot receive versions or new evaluations (409); historical reads/reviews still work. DELETE again returns 409. Historical active versions can be evaluated explicitly, never silently substituted with latest. PUT/DELETE expected_version must match latest; appeal/decision expected_revision must match current evaluation revision. SQLite transactions enforce these comparisons and uniqueness to prevent lost decisions. No locks held while waiting for provider calls.

### Organizer adapter boundary

POST dataset-imports invokes a server-side GET against a configured organizer URL, preserving its other supplied query parameters and replacing/setting group_id. No client-supplied arbitrary URL. The fixture `organizer-response.json` shows the documented external envelope `{error:string,isSuccess:boolean,data:{dataset_group_id:string,total_records:integer,records:SourceRecord[]}|null}`; unsuccessful upstream replies may vary, so handle isSuccess=false without assuming data exists. Success requires group ID equality, count equality, valid records and unique source IDs. Atomic batch import: any invalid record or content conflict rolls back the whole import. Existing identical records count as unchanged. Return internal conversation_ids in source record order. Source timestamps are never regenerated. The actual signed DEV URL is embedded in the G p. 3 button hyperlink; configure it privately as ORGANIZER_DATASET_URL, never commit its signature or expose it to the browser. No configured organizer URL => 503 organizer_not_configured. Never synthesize a DEV URL or require the sample count of 65.

### Errors

All non-2xx responses (including FastAPI validation errors) use `{error:{code:string,message:string,details:{path:string,message:string}[]},request_id:string}`. details may be empty. No stack traces/provider secrets. Paths use request property paths, e.g. configuration.criteria[0].weight. Nonexistent path => 404; unsupported method => 405 method_not_allowed. Invalid JSON/schema/query => 422 validation_error. Unknown filters rejected with 422. Generic unexpected internal failure => 500 internal_error.

| HTTP | code | Meaning |
|---|---|---|
| 404 | not_found | Referenced resource/version missing |
| 409 | source_conflict | Existing source identity has different immutable content |
| 409 | version_conflict | expected_version or expected_revision stale |
| 409 | checklist_archived | Mutation/new evaluation uses archived checklist |
| 409 | evaluation_not_ready | Appeal submitted before success |
| 409 | duplicate_appeal | Criterion already appealed |
| 409 | appeal_resolved | Second decision |
| 422 | validation_error | Malformed input, invalid configuration, unknown IDs inside evidence/criterion references, unsupported N/A |
| 422 | invalid_judgment | Invalid reviewer replacement, including missing evidence or scale mismatch |
| 502 | organizer_failure | Upstream non-success/status/error, invalid JSON/envelope/record/count/group ID |
| 503 | organizer_not_configured | Organizer URL has not been supplied |
| 504 | organizer_timeout | Organizer GET timed out |

Provider failures happen after the 202 and are represented by Evaluation.status=failed and provider.error, not a successful score or a GET transport error. Provider-not-configured maps to a failed attempt with provider_auth and retryable=false. Do not expose credentials in its message.

## Request/response examples

Import request: `{"group_id":"DEV"}`; illustrative response: `{"group_id":"DEV","imported":1,"unchanged":0,"conversation_ids":["conv_demo"]}` (not a claim that DEV has one record).

Upload request and response: `fixtures/upload-request.json` → Conversation shape in `fixtures/conversation.json` (upload source would be `{kind:"upload",group_id:null,conversation_id:"upload-demo"}` and a newly generated internal ID).

Create checklist: take `fixtures/checklist.json` and omit checklist_id/version; response is ChecklistVersion. Update: `{"expected_version":1,"configuration":<ChecklistInput>}` creates version 2. To replace a criterion change its ID and configuration; historical evaluations stay pinned to version 1.

Evaluate request: `{"conversation_id":"conv_demo","checklist_id":"checklist_seed","checklist_version":1}`. Initial 202 has the Evaluation shape with status=queued, completed_at=null, results=null, appeals=[], provider.error=null. Polling examples: `evaluation-original.json`, `evaluation-failed.json`.

Appeal request: `{"expected_revision":1,"criterion_id":"c07","comment":"Чат оборвался до возможности завершения."}`. 201 uses the appeal in `evaluation-reviewed.json` with status=pending and decision=null, incrementing evaluation revision to 2.

Decision request: `{"expected_revision":2,"action":"change","reason":"Подтверждена неприменимость завершения.","replacement":<Judgment for c07 from evaluation-reviewed.json decision>}`. Response: `evaluation-reviewed.json` (revision=3). Confirm uses action=confirm and replacement=null. Error envelope example: `fixtures/error.json`.
